# 性能

本页讲的是真正决定一个 TypePHP\Qt 应用「跟手还是发黏」的三件事。下面所有结论都对着真实引擎
（`cpp-src/qt_bridge.cc`）核对过，不是猜的。

**如果你在做一个小表单，这一页可以跳过。** 默认实现在几百个控件以内都没问题。等列表变长、
页面开始闪烁，或者明显能感觉到帧预算被吃掉时，再回来读。

## 一帧里发生了什么

循环由 PHP 驱动，所以一帧是：

```
pollEvents()  →  分派处理器  →  你的 view() 构建函数跑一遍  →  qt_window_render(tree)
                                                                    │
                     C++：遍历树 → 逐节点签名 → 和上一帧 diff
                          → 只应用变化的属性 → Qt 布局 / 重绘
```

前两步归 PHP，最后一步归 Qt。你能动的杠杆是第 2、3 步做多少事，以及树里**实际变了**多少 ——
而不是 Qt 画得多快。

帧节奏是固定的 16 ms 一拍（`QTimer::singleShot(16ms)`），也就是说构建函数**每秒被调用约 60 次**，
一直如此。你放进构建函数里的任何东西都是「每帧成本」，不是「一次性成本」。

## 规则一 —— 每个动态子节点都要显式 `id`

这不是代码风格问题，它决定了节点是「更新」还是「重建」。

没有 `id` 的节点会拿**结构路径**（`_p0.1.2`）当身份，而这个路径**只在同一帧内**稳定。
在列表靠前的位置插入一行，后面所有节点都会位移：原来的 `_p0.1.3` 现在在 `_p0.1.4`。
引擎没法知道「这个控件只是挪了位置」，它只会看成「旧的删掉、新建一个」。

症状按通常出现的顺序：

- 打字时输入光标跳到开头（或直接跳出输入框）；
- 刷新一次表格，选中行被清空；
- 滚动位置回到顶部；
- 长页面上出现**空白和闪烁** —— 没在同一趟布局里被重建的控件脱离了原位。

所以：`table`、`tree`、`list`、`tabs`/`stack` 的页面，以及任何条件分支里的孩子，
都必须带显式 `id`。

```php
// 正确：身份跟着任务走，不跟着它的位置走
foreach ($state['tasks'] as $task) {
    $rows[] = [
        'id'     => 'task_' . $task['id'],
        'cells'  => [$task['id'], $task['title'], $task['status']],
    ];
}
```

## 规则二 —— 构建函数里不要有昂贵操作

构建函数每秒跑 60 次。在里面做一次 2 000 行的 `usort()`（5 ms），每秒就烧掉 300 ms 的 CPU
去反复决定同一件事。

可行的形状是：

- **处理器和定时器改状态。** 过滤、排序、解析、读文件、发 HTTP —— 全放这里，只做一次。
- **构建函数只格式化状态。** 把状态映射成控件，别的一概不做。
- 需要活数据？用定时器刷新，不要每帧刷新：

```php
$app->setTimer('refresh', 1000);            // 1 Hz，不是 60 Hz
$app->on('refresh', 'timer', function () use (&$state) {
    $state['tasks'] = loadTasks();          // 昂贵的那部分，每秒只做一次
});
```

`setTimer($id, $intervalMs)` 每次调用都会重新计时，间隔 ≤ 0 即停 —— 所以切换刷新频率本身也只是
一次状态改动。

## 规则三 —— 签名是逐节点、逐帧算的

在碰 Qt 之前，桥接会给每个节点、每个属性算一个哈希签名，没变的直接跳过
（`qtSignature()` 用的是哈希而不是拼接字符串，正是为了让这一步足够便宜）。

这就是为什么改 5 000 行表格里的一行只会重绘那一行。但它也意味着 `rows` / `nodes` 这份载荷
**即使什么都没变，每帧都要被遍历并哈希一遍**。上千行的话，PHP 侧（构造数组）和 C++ 侧（哈希）
都是每帧成本。

对热的、只追加的数据 —— 日志、进度、流式行 —— 用 `patch()`，别每帧描述整张表：

```php
$app->patch([
    ['op' => 'call', 'id' => 'log', 'method' => 'appendRows',
        'args' => [[['10:32', '启动'], ['10:33', '就绪']], ['l1', 'l2']]],
]);
```

`call` 是命令式旁路：它改动控件但不改你的树，桥接会自动作废受影响属性的 diff 签名，
于是下一次 `render()` 一律以树为准重新同步。实际后果是：这样追加的行**只活到下一帧**，
除非你也把它写进状态。当「产生这些行的状态改动」和「这次追加」是同一件事时用它，两者就一致了。

已实现的 `call` 方法见 README 的增量补丁表；同一次调用里的 `set` 走普通声明式属性。

## 量出来，而不是猜

设 `QT_DEBUG_TIMING=1`，每帧会把渲染开销打到 stderr：

```bash
QT_DEBUG_TIMING=1 ./build/hello          # Windows：$env:QT_DEBUG_TIMING="1"
```

把它读作「C++ 做 diff + apply 花的时间」。如果这个数字很小、界面却仍然慢，那成本就在 PHP 构建
函数里，不在桥接 —— 用 `hrtime(true)` 量一下构建函数里那段慢的。

开发时设 `QT_DEBUG_STRICT=1`。未知控件类型、未知属性、未知 `patch` method 是**故意**静默忽略的
（这正是让老应用能继续对着新版桥接编译的原因），所以属性名写错只会……什么都不发生。严格模式会把
这些全部变成 stderr 上的警告：

```bash
QT_DEBUG_STRICT=1 ./build/hello
```

## 启动、体积与打包

三件互不相干的事，对应三个不同的杠杆：

| 口径 | 杠杆 | 说明 |
|---|---|---|
| 启动 | 无需配置 | 桥接直接编进你的应用；除了 QApplication 之外没有需要初始化的运行时 |
| 产物体积 | `qtphp build --nano` | 参考示例 4.3 MB vs 25.6 MB；`php-nano` + PHPX 源码编进去，不链任何 PHP 运行时 |
| 打包体积 | `qtphp package`（默认） | `--no-opengl-sw` 从 `dist/` 去掉 20 MB 的软渲染回退 |

裁剪打包产物时**不要**跳过 `tls` / `networkinformation` 这两个 Qt 插件：`qt_http_request()` 走的是
`QNetworkAccessManager`，缺了 `tls` 所有 HTTPS 请求都会失败。

## 一份清单

- [ ] `table` / `tree` / `list` / 条件分支里的每个孩子都有显式 `id`。
- [ ] `view()` 构建函数里没有 I/O、没有网络、没有对大集合排序。
- [ ] 任何会无限增长的东西都用 `patch(['op' => 'call', …])` 或分页状态，而不是每帧全量重描述。
- [ ] 定时器的频率等于数据真实变化的频率，不是帧率。
- [ ] 至少在卡的那个界面上跑过一次 `QT_DEBUG_TIMING=1`。
- [ ] 正常跑一遍时 `QT_DEBUG_STRICT=1` 没有任何警告。
